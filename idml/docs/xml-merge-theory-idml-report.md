# 从通用 XML 三方合并到 IDML：MR01—MR14 测试发现与理论反思

日期：2026-11-06。实施分支：`V1_1_3-Kaining-2`。

## 结论与证据边界

本项目没有找到足以推翻 Lindholm 论文核心算法的反例。已验证的问题主要是：本仓库
早期实现没有完整兑现模型的匹配、关系协调与重建前提；部分行为属于论文明确允许的
宽松策略，而项目选择了更严格的策略；另一些正确性要求来自 IDML 的跨 part 引用、
布局依赖和 ZIP 写入工程，不能从通用 XML 树定理直接推出。

“原算法”在下文指本仓库 MR01 前的实现（参考 `28cf140`），**不是论文作者 3dm 源码**。
我们核对了论文原文与本仓库历史，没有复现或审计作者完整 3dm 实现。通过有限测试不等于
证明本仓库已完整复刻论文，也不等于证明全部 XML/IDML 输入都能正确合并。

MR13 的 25 个场景、125 次正式测量及冻结门禁已通过。MR14 已实现自动化验收和严格
真实证据门禁，但用户确认尚无获授权的真实三方样本与 InDesign 打开/保存/关闭/重开
记录：计划 4 组，实际提供 **0 组**，发布结论为 **不就绪**。不能把下文的自动化发现
表述为真实排版验收完成。证据与执行结果见 [MR14 证据表](xml-merge-test-evidence.md)。

论文依据：Tancred Lindholm, *A Three-way Merge for XML Documents*。本次重新读取了用户
提供的 10 页 PDF；页码均指 PDF 页内页。关键依据为 §2.3（p3）、§3.1（p4—5）、
§4—5（p5—6）、§6.1—6.4（p6—8）、§6.5—7（p8—9）、§9（p10）。
原文 PDF SHA-256：`69663ca80dfae6832f2f951536bed96cbfafc0e10a1c07d5f385a0e3d1b86287`。
本地干净回归受测实现为 `f2bca0a`：946 项 Scala、22 项 Python 通过；
1 项既有忽略测试单列，真实应用验收不计入通过数量。

## 为什么必须区分 E、Δ 和最终树

在相同匹配下，状态差异给出编辑集合 E；协调后得到关系集合 Δ，最后重建可达树 Tm。
`E⊆Δ` 只能说明编辑仍在关系集合中。一个子树若从根不可达，编辑即使留在孤立关系里，
用户打开文档也看不到它。论文 §6.3 已明确给出可选检查 `(Δ−Tm)∩E=∅`；§6.4 的最终树
编辑保留性质以启用这个检查为条件。本项目没有“发现论文忘记可达性”，而是测试暴露了
实现和项目严格策略未接通的问题。

类似地，原子 content 层的 `Δ⊆T*` 与 IDML 逐属性组合必须分开验证。一侧改 FillColor、
另一侧改 StrokeColor 后生成的新属性组合可以是项目允许的结果，不能因为这个完整
Content 对象不曾原样出现在输入中，就用原子层断言将其误判为凭空内容。

## 逐项发现、归因与解决位置

### 1. 同路径不等于同节点；重复 Self 不能静默覆盖

**现象。** 无 Self 的 A/B/C 段落，左删 A、右改 C。如果用绝对路径当跨版本身份，原 B
移到 A 的路径，C 的修改可能被错误关联或丢失。另一类输入在同一版本出现重复 Self，
早期 `.toMap` 会覆盖其中一个节点；返回“匹配成功”掩盖了输入错误。

**归因。** 这是匹配前提未满足，不是论文定理错误。§4 p5 要求匹配一对一并满足 R1—R5，
并明确把准确构造匹配关系作为输入前提；论文没有保证仅靠位置就能恢复未知编辑历史。

**修复与证据。**

- [TreeMatcher.scala](../../core/src/main/scala/com/phasmidsoftware/xmldoc/merge/TreeMatcher.scala)
  的 `index` 在 matcher 边界拒绝重复 Self，错误包含身份、分支和路径。
- [ContentMatcher.scala](../../core/src/main/scala/com/phasmidsoftware/xmldoc/merge/ContentMatcher.scala)
  先保留精确内容锚点，再处理剩余候选；重复内容的数量变化无法可靠判定时保守失败；
  未匹配子树的后代也全部进入 unmatched 集合。
- [ThreeWayMerger.scala](../src/main/scala/com/phasmidsoftware/xmldoc/idml/ThreeWayMerger.scala)
  的 `matchedLabels` 把匿名子节点匹配接到公共入口，新增匿名后代按最近 Self 祖先划定
  身份范围，避免两侧同一原始路径上的不同新对象共享身份。
- 回归：`TreeMatcherSpec`、`ContentMatcherSpec`、`TreeMatcherIdmlSpec`、
  `ThreeWayMergerSpec` 的 A/B/C、歧义删除、移动后匿名后代编辑，以及 MR10 固定对照。
  代表提交：MR04 `0bba059`、MR08 `a3b7bc6`、整合 MR12 `34756c1`。

**尚未解决的普遍问题。** 相同内容、相同数量的多个节点仍可能具有不同真实历史。
目前的文档顺序约定不构成“恢复历史”的证明。未来需要显式稳定 ID、领域身份或可审查
的歧义结果；不能继续增加位置猜测来宣称支持任意 XML。

### 2. 把旧父关系误当成新编辑，产生错误的唯一父诊断

**现象。** 父节点下兄弟顺序变化时，新的 PCS 邻接关系也会提到仍在原父节点下的节点。
早期 `parentOf(leftEdits.pcs)` 把这种提及当成“该侧新要求的父节点”，可将一侧真实重父
与另一侧保留旧父误判为双边换父冲突。

**归因。** 这是状态差异解释不完整。§3.1 图3（p4—5）专门说明子节点重排不应固定其
共同父节点的位置；§6 的编辑优先于 base 旧关系，不等于把双方所有关系都当成新意图。

**修复与证据。** [PcsMerger.scala](../../core/src/main/scala/com/phasmidsoftware/xmldoc/merge/PcsMerger.scala)
的 `parentEdits` 从完整的预匹配输入关系求父映射，仅将相对 base 真正变化的父值用于
冲突协调。`PcsMergerSpec` / `ThreeWayMergerSpec` 同时验证父移动加内部重排成功、双方
相同新父成功、两个不同新父冲突，并逐项交换 left/right。代表提交：MR07 `6927463`。

原来的某个 group/ungroup 用例即使最终仍应因删除区域编辑而冲突，也不能继续用错误的
`parent of x/y` 原因解释它。现在把“是否冲突”和“为什么冲突”都纳入完整断言。

### 3. 单靠 successor 覆盖会留下旧位置残余；重建成功不是一致性证明

**现象。** g 从 p 移到 q 后，旧关系 `p:g→ListEnd` 可能仍留在集合里；根路径重建能忽略
这条残余，让局部检查误以为完整关系集合正确。更严重时，重复父、循环、断链、缺失
content 或未解决冲突可能被映射覆盖/遍历方式掩盖。

**归因。** 这是关系协调与重建边界的实现缺口。论文 §5—6 先要求一致的 Δ，再谈恢复 Tm；
它没有授权“能沿某条路径构造一棵树”代替全部一致性和编辑保留检查。

**修复与证据。** `PcsMerger` 的 `withoutObsoleteBaseLinks` 清除不再使用的旧 base 链，
不借清理过程随意删除新编辑；[PcsTreeBuilder.scala](../../core/src/main/scala/com/phasmidsoftware/xmldoc/merge/PcsTreeBuilder.scala)
检查关系、父/兄弟一致性与循环，并拒绝从有冲突的结果重建。MR06 完整关系集合断言首先
暴露残余；MR08 加强重建失败契约；`PcsTreeBuilderSpec` 和 IDML 对应测试保留负向证据。
整合时保留较完整的 MR08 清理逻辑并运行全部 MR06 对照，而不是叠加两套互相冲突的清理。

### 4. 格式空白也是节点：序号身份导致兼容插入假冲突

**现象。** 两侧在不同间隙插入对象时，缩进文本的序号改变，两个无关插入被解释成修改
同一个字符节点。case 04 实际跑 corpus 后才发现问题；只检查对象 Self 与“无冲突”的
简化小树不足以发现它。新增对象内部的匿名 Properties 也不能按原始路径共享身份。

**归因。** 这是 XML 表示与匹配实现的问题，IDML 常见的格式化 XML 把它放大了；并不是
IDML 独有，也不是论文的关系代数自行产生矛盾。论文假定正确匹配，未替实现者定义每种
序列化空白的稳定身份。

**修复与证据。** [Pcs.scala](../../core/src/main/scala/com/phasmidsoftware/xmldoc/merge/Pcs.scala)
对严格交替的缩进/元素列表，把空白身份锚到其后已匹配元素或尾边界；公共入口的
`matchedRelations` 还支持混排、连续 text/CDATA 的独立顺序，并给文本专用父节点保留
既有 slot 约定。**没有 trim 正文，也没有删除空白来获得绿灯。**

回归包括 case 04 全包目标、MR09 的缩进保留与双侧空白修改冲突、MR12 的带匿名后代
独立插入、混排文本更新与元素插入。见 `PcsMergerSpec`、`ThreeWayMergerSpec`、
`ThreeWayCorpusSpec`、`ThreeWayPackageCorpusSpec`。代表提交：MR09 `5f7fdd8`、MR12 `34756c1`。

这套锚点只覆盖已冻结的模型，不应被宣传为所有混排 XML 的规范化算法。改变 XML 的
逻辑文本分组仍可能改变可合并性，这是后续领域建模要显式研究的部分。

### 5. Delete/Edit 只查节点属性，漏掉深层正文与插入

**现象。** 删除 Group 的一侧没有看到另一侧深层文本修改/新增子节点时，早期属性级检查
可能无冲突返回；更新还在孤立 Δ 中，但在最终文档中消失。反过来，仅凭原祖先被删就
报告冲突，会误伤已移到最终可达树的子节点编辑。

**归因。** 论文 §6.3 p7—8 把 Delete/Edit 列为 **optional**，并公开承认宽松合并会丢掉
被删区域的编辑。宽松模式本身符合论文；项目 MR01 明确选择严格模式后，未在公共入口
兑现它才是本项目的漏洞，不能写成“论文声称保留却遗漏了这种情况”。

**修复与证据。** `ThreeWayMerger.deletedSubtreeConflicts` 遍历候选可达图，在真正不可达
的 base 区域比较两侧内容及子列表；它复用与合并相同的预匹配关系，以免检查时换了一套
身份。测试覆盖 1/4/12 层正文、深层插入、Group 子列表真实变化、忽略字段负向对照，
以及移出被删 Group 后的编辑保留。MR10 另检查最终可达 ledger，而不只检查 E 仍在 Δ。

### 6. 两个旧测试预期本身也错了：不能让算法迎合错误 oracle

- **case 10 解组 + ItemTransform 更新：** 旧强制冲突预期不是论文能直接推出的。
  MR03 `d047951` 保留原输入字节，将其改为完整成功目标；另增 **10b**：r3 从共同 base
  的 g1 出发，左到 Spread、右到已有 g2，真正表达两个不同新父要求。
- **08b 不重叠单词修改：** 在本轮 `strict-text-node-v1` 下，同一文本节点的两个不同
  内容值仍是原子 Update/Update 冲突。单词不重叠不自动使它可合并；token merge 是另一种
  粒度与 policy，不能在同一 profile 里同时接受成功和冲突。

前者是 oracle 纠正与领域边界澄清，后者是模型粒度选择；都不是论文核心算法被反证。
`CorpusContractSpec`、生成器与 Python 篡改测试将 schema/profile、16 组、8/8 状态、
case10/10b 和原始哈希固定下来。[规格](xml-merge-test-spec.md) 也明确：XML 能保留
ItemTransform 字符串不等于理解坐标或证明 InDesign 页面位置正确。

### 7. 属性细化与波动元数据：必须同时定义比较和保留

**现象。** 原子 Content 把不同属性的独立更新也视为整体不同；IDML 入口则需要允许
FillColor 与 StrokeColor 分别来自两侧。另有 LinkImportTime、StyleUniqueId 自动变化：
仅“比较时忽略”还不够，输出如果随左右顺序任意选值，仍不满足确定性；双侧同身份
新增且仅这两个字段不同时，旧实现还会误报整个插入节点冲突。

**归因。** 原子性选择和元数据策略，不是 PCS 唯一性规则出错。论文 §7 p9 自己就记录了
OpenOffice 元数据并发变化的问题。逐属性细化是项目扩展，不能反过来说论文原子定义有错。

**修复与证据。** `Merger.reconcileUpdates/reconcileInserts` 与 `PcsMerger` 的内容协调
分别遵守各自粒度；已有节点保留 base 的忽略字段，新节点保留来源整组字段，双侧同身份
且显著内容相同则按已冻结的规范属性 UTF-8 字节顺序选完整一组。MR10 同时测试左右交换、
属性排列、XML 转义与非 BMP 字符。原始 PCS 集合边界只在无忽略字段的生成数据上断言；
IDML 组合结果逐属性验证来源。见两个 `*PropertiesSpec`，代表提交 `9d229c6`。

### 8. 合法 XML 树不等于合法 IDML 包，更不等于没有领域意图冲突

**现象。** Story、TextFrame 和 Next/Previous/ParentStory 分布在多个 part。合并后的每个
XML 都可以良构，却留下悬挂引用、非互反线程或环。06b/13 还展示另一层问题：引用即使
静态合法，一侧删除/重连 Story 布局、另一侧修改相关正文，也可能丢失并发编辑意图。

**归因。** IDML 领域约束。论文 §9 p10 将领域专门化作为后续方向，并没有证明任意 XML
词汇的应用语义。字符串属性在通用树模型里不自动成为跨文件约束。

**修复与证据。** [IdmlReferenceValidator.scala](../src/main/scala/com/phasmidsoftware/xmldoc/idml/IdmlReferenceValidator.scala)
在候选包逻辑视图检查受支持的引用、身份、互反链接与环；`IdmlPackageMerger` 在写包前
执行静态检查和 base/left/right 的 Story 级保守依赖检查。不是把所有字符串都当 ID，也
不推断排版后哪个字符落入哪个 frame。

06b/13 中 tf2 的删除/重连伴随 tf1.Next 的变化，两端都构成领域报告。整合后的 oracle
适配从已冻结输入事实核对完整两条报告，而不是只检查“包含 tf2”或删除额外信息。
回归：`IdmlReferenceValidatorSpec`、`IdmlPackageMergerSpec`、两个 corpus suite 与 MR14
跨层验收；代表提交 MR11 `e138474`、MR12 `34756c1`。

Story 级依赖是保守规则，不能据此声称已恢复精确排版意图。未来可以细化依赖范围，但
必须用真实样本证明降低假冲突没有增加静默损失。

### 9. 冲突正确仍可能损坏文件：ZIP 写入与失败原子性是另一份契约

**现象。** 原 driver 顺序修改 ours；若第二个 part、designmap 或最终写出失败，文件可能
只改了一半。XML 重序列化还可能丢掉未建模 PI，或改变未触及 entry 的原始字节。

**归因。** 工程实现问题，不是论文关系算法的逻辑反例。论文没有定义 Git driver 的
退出码、文件系统原子替换或 ZIP entry 保留策略。

**修复与证据。** [IdmlMergeDriver.scala](../src/main/scala/com/phasmidsoftware/xmldoc/idml/IdmlMergeDriver.scala)
的 `applyAtomically` 在同目录 staging 副本完成全部修改、manifest 补丁、重新打开和
候选校验，最后原子替换；不支持原子替换时失败，不作破坏性回退。未改 entry 保留 ours
字节，designmap 仅补 part 引用。写入钩子按调用隔离，支持独立目标并发。

MR12 测试覆盖多个故障阶段、真实损坏输入、子进程退出 0/1/2、资产与 PI 保留；MR14
`IdmlMergeAcceptanceSpec` 再核对从输入到候选、失败不写、写后重读的短完整链路。
这证明的是函数返回失败的原子性，不是断电持久性或同一路径并发安全。

## 有没有发现“符合论文但理论本身有问题”？

目前没有核心形式规则自相矛盾的证据。可以确认的，是论文自己承认、项目必须面对的
**模型适用范围**，以及本仓库尚无普遍正确性证明的启发式实现：

1. **身份不是从 XML 外观必然可恢复的。** §4 把正确匹配当作前提；重复无 ID 内容的历史
   可能不可辨。应用必须提供稳定身份或承认歧义。
2. **逻辑编辑单位会改变可合并性。** §7 p9 记录了 37 个研究用例中的 35 个成功和两类
   不适配示例，包括文本抽取/包装后逻辑实体被切成不同节点。IDML 样式包装、段落和正文
   与此高度相关；我们的有限包装回归没有证明任意包装与正文并发编辑都可合并。
3. **树的结果不等于应用可观察结果。** 合法结构与字符串保留不足以证明视觉位置、溢出
   文字、字体和链接资源的正确性。尚缺真实样本，因此这部分只能提出待验证条件。
4. **宽松/严格是明确策略分叉。** 不启用 optional Delete/Edit 的输出可能符合基础算法，
   却不满足本项目“不静默丢编辑”的产品要求；这里需要配置与契约，不是改写数学结论。

这些结论支持研究更明确的前提、领域适配和语义验证，而不支持宣称“IDML 推翻了论文”。

## MR13 能说明什么，不能说明什么

正式测量：32/128/512 个元素节点；种子 13/37/73；操作预算 0/4/16；另有每叶 64 KiB
文本场景。操作按四类等概率抽样、独立上下文约束与拒绝重采样，记录实际分布与 E。
125 次正式测量均校验完整独立结果并通过预冻结门禁。

纯合并/重建最大约 7.280 ms，总流程最大约 26.960 ms。拟合得到负的编辑系数 c2，说明
该小矩阵及噪声不能支持单调编辑成本的因果解释；R²≈0.889 不是复杂度证明。
论文 §6.5 的 O(n log n) 还假定单节点内容大小有界；§7 图6明确排除解析与匹配。本项目
也将它们分段，另列长文本压力，不能用长文本慢就否定该有条件的界。

当前基准测的是 Self 生成树的预匹配 PCS 核心及最小包写入，不是完整真实 IDML driver
或匿名匹配最坏情况。源码审查还提示后续需单列的风险：`matchedRelations` 的后缀扫描、
`ContentMatcher` 的重复子树归一化、严格删除检查逐节点查询集合，可能在特定形状产生
超线性工作；这属于待测复杂度风险，**不是本轮已测得的性能失败**。后续应增加深链、
高扇出、重复匿名内容、大量删除和真实包，再决定缓存/索引优化。

原始数据、环境、校准、门禁、分布与拟合全部见 [性能文档](xml-merge-performance.md)。

## IDML 对更一般 XML 理论的反思价值

IDML 不是仅仅一个“大 XML”。它是带有稳定身份、多个有序树、跨树引用、资产及渲染语义
的包。因此，从单树 PCS 正确性到可交付文档，至少有四个独立的证明/证据边界：

1. 匹配关系是否满足形式要求，并真的对应领域中的同一对象；
2. 核心协调是否生成一致且保留所选策略编辑的可达树；
3. 多树组成的候选是否满足引用约束及并发意图依赖；
4. 序列化、文件事务和应用观察是否保留这些结果。

第一层不能从后续集合运算的正确性倒推，第三、四层也不能从 XML 良构性推出。这使
IDML 成为检验“通用内核 + 明确适配契约”的有价值实例：PCS 内核可以保持通用，领域层
定义身份、逻辑单位、引用和依赖；事务层保障落盘；应用层验证视觉。需要研究的是这些
层的组合条件和失败诊断，而不是把一切 IDML 规则硬编码进一般 PCS。

可推广的研究问题包括：如何表示并验证跨文档匹配的置信度；怎样把 token/段落/包装的
逻辑单位映射到原子内容模型；怎样组合多树引用约束与编辑保留；怎样区分保守冲突、
信息不足和真正矛盾；以及怎样为渲染应用定义不等同于 XML 字节相等的可观察语义。
这些是由本项目提出并部分实现的方向，尚不是新的完备理论或已经得到证明的定理。
