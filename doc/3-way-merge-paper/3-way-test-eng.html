Part 1 · Paper §3.1, §5, §6

Expected outcomes come from four sources

The source of each expectation is fixed before any assertion is written. Expectations follow the rules, not the current behavior of the implementation.

Delete/Edit is an optional conflict§6.3 (p. 8): the basic merge lets edits remain in deleted subtrees, and keeping such edits from being lost takes an extra check. When the project adopts the strict policy, the tests state it explicitly.
Text token merge is a project policy§2.3 (p. 3) treats the character data of a text node as its content; §7 (p. 9) discusses the limits of partial text matches and of changes to formatting structure. Whether two non-overlapping edits in one text node merge automatically is decided by project policy.
Cross-file references get their own test layerReference semantics across XML files, such as ParentStory and NextTextFrame, lie outside the generic PCS tree model. §9 (p. 10) lists specialization with domain-specific knowledge as future work.
Part 2 · Paper §2.1, §3, §3.1

Two kinds of samples: minimal XML and full IDML

Following §3 (p. 4): prepare the input XML, state the merge task and hand-craft the expected result. Small abstract cases check single rules; real document cases check product behavior.

Minimal XML sample: a move on the left, a content edit on the right

The expected result satisfies all of the following:

  • The merge succeeds
  • Child order is a, c, b
  • b.FillColor == Red
  • b occurs exactly once
  • All other nodes and attributes keep their values
RationaleA move combined with a content edit is the pairing of “reorganization in the large” with “updates to the details” stressed in §2.1. It tests the core capability of the paper more directly than detecting a move alone.

Full IDML sample: final product behavior

When building samples:

  • Both branches come from the same closed and saved base copy
  • Unchanged nodes keep their original Self
  • New nodes get identities that cannot collide by accident
  • For nodes without Self, the expected matching is recorded separately
  • expected is never generated by the merger under test
Self and matchingKeeping Self is a reliable sample policy of the project. §4 (p. 5) requires a correct node matching (R1 one-to-one, R2–R5 an equivalence relation); it does not prescribe Self.

§3.1 rule 7d (p. 5) lists this case as changes too close to merge safely. “The left swaps a and b, the right swaps c and d” does not make the two edits independent.

Beyond the same-node case “delete r / edit r”, a strict Delete/Edit check reaches into the whole deleted subtree.

Part 5 · Paper §5, §6, §6.3

Success cases compare the full result; conflict cases check the conflict objects

Success cases assert the complete Tm; conflict cases assert the conflict record field by field. Both rest on the set relations of §6.

Success cases: full-result comparison

Full-result comparison

val actual = ThreeWayMerger.merge(base, left, right)
actual shouldBe Right(expected)

Extra relations and missing edits both surface.

Partial assertions only

result.conflicts shouldBe empty
result.relations.pcs should contain(expectedRelation)

The output may still contain extra relations or miss other edits.

For real XML, direct object equality depends on attribute order, so an explicit semantic comparator is used:

AttributesCompared as a set

Assertion granularity§5 (p. 6) lists four consistency constraints: unique content, unique parent, unique predecessor and unique successor. One business conflict can map to several relation contradictions (two in Figure 6a); business-level tests assert the set of conflict objects, while PCS-level tests assert the complete set of relation conflicts exactly.
Part 6 · Paper §6, §6.4, §7

Property tests: symmetry, identities and preservation of edits

Property tests check that the rules themselves hold; they complement the concrete examples.

Basic identities

merge(B, B, B)= Bneither side changed
merge(B, L, B)= Lonly the left changed
merge(B, B, R)= Ronly the right changed
merge(B, L, L)= Lboth sides made the same change

These relations hold under semantic comparison for normal inputs, declared policies and agreed ignored fields. They are basic checks derived from the paper’s model.

Preservation of edits: assert the final document

No structure or content made up§6 (p. 6) requires E ⊂ Δ ⊂ T*: to remove a contradiction, the merger neither invents relations absent from all three versions nor picks arbitrary new values. With attribute-level reconciliation, attribute values from different branches can combine into a new element as a whole; the tests check the source of each attribute value.
Part 7 · Test plan, part 7

Traceability for the 15 existing corpus cases

Following the test plan, each case is tagged with its expectation source and follow-up action. Border styles follow the page notation.

06b and 13When one side changes TextFrame structure or references and the other changes Story text, the paper’s generic tree model does not flag a conflict by itself. When the product requires a conflict, a business rule states which user intent could be lost or changed. ThreeWayMerger combines attribute reconciliation with PCS structural reconciliation; cross-part semantic dependency checks are confirmed by separate tests.
Part 8 · IDML and engineering acceptance

End-to-end checks on full IDML packages

Successful outputs are reopened and checked item by item; conflict outputs leave ours unchanged. These checks are IDML and engineering acceptance requirements, not items prescribed by the paper.

Checklist for successful outputs:

  1. Reopen the output IDML
  2. Check that each expected part exists, or is removed
  3. Parse the relevant XML and compare the full semantic result
  4. Check that part references in designmap.xml match the actual files
  5. Check that target identities exist, within the reference scope defined by the project
  6. Check that TextFrame previous and next references agree and form no illegal cycle
  7. Check that unedited resources and binary assets are preserved
  8. Open and save representative real samples in InDesign and check the expected behavior

Conflict output: inputs stay unchanged

Part 9 · Paper §6.5, §7

Implementation order and scale tests

Ordered by dependency: sources and core scenarios first, then stronger assertions, then whole-package acceptance and scale tests.

  1. Add an expectation source to each of the 15 existing samples: paper rule, project refinement or IDML rulesee part 7
  2. Add the core paper scenarios: move with content update, parent move with child reordering, guards, ancestor deletion with descendant editsee part 4
  3. Add full-result assertions: from conflicts.isEmpty to complete tree comparisonsee part 5
  4. Run the whole corpus parameterized: each case in the normal order and with left and right swappedsee part 6
  5. Add tests for matching without Self and for mixed textsee part 4
  6. Add whole-package reference checks and real InDesign acceptance samplessee part 8
  7. Scale tests: time parsing, matching, merging and package writing separately
Basis for the scale-test design§7 (p. 9) times generated trees with varying numbers of nodes and edits, with insert, delete, move and update equally likely, and fits the execution time to t = c₀ + c₁n + c₂e. Scale tests can reuse this design.
