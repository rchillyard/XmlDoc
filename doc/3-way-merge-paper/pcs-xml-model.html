01

XML 树的定义

节点 = 身份 + 内容；整棵树用两种关系表达

论文把 XML 文档视为一棵有顺序的、每个节点具有唯一标签的树。每个节点承载两类信息：节点身份（label，例如 a0、b0）与节点内容（元素名、属性、文本等）。

整棵树随后被两种关系完全表达：Content 关系描述“某个标签的节点内容是什么”，PCS 关系描述“节点之间的父子与前后顺序”。这两组关系放进统一集合后，就能用集合差集来表达文档之间的编辑。

03

PCS 关系 pcs(r, p, s)

父子关系与 sibling 顺序，一次编码两件事

论文定义 pcs(r, p, s) 表示：r 是 p 和 s 的父节点，且在 r 的有序子节点列表中，s 紧跟在 p 后面。

Pcs.scala · 实现line 20
case class Pcs(
  parent: String,
  predecessor: Sibling,
  successor: Sibling
)
示例
Pcs(
  "spread",
  SiblingNode("u1"),
  SiblingNode("u2")
)

在 spread 的子节点列表里，u2 紧跟 u1，且二者父节点都是 spread。

为什么比普通 parent-child 边更适合三路合并：PCS 同时编码父子关系与 sibling 顺序，一条关系里就带上了“谁在谁后面”，因此顺序变化也能通过集合差集被检测到。
04

列表边界标记 ⊣ ⊢

让第一个和最后一个子节点也有前驱、后继

为使首、末子节点也拥有前驱与后继，论文引入两个不能被编辑的特殊标记：⊣（列表开始）与 ⊢（列表结束）。

Pcs.scalaline 12 · Sibling 密封类型
sealed trait Sibling

case class SiblingNode(label: String) extends Sibling
case object ListStart extends Sibling  // ⊣
case object ListEnd   extends Sibling  // ⊢

若某个 Spread 的子节点顺序是 u1, u2，则展开为一条带边界的链：

⊣→ u1→ u2→ ⊢
Pcs("spread", ListStart, SiblingNode("u1")) Pcs("spread", SiblingNode("u1"), SiblingNode("u2")) Pcs("spread", SiblingNode("u2"), ListEnd)
开头插入 · 结尾插入 · 交换 · 删除首末 —— 全部统一为 PCS 关系变化

叶节点也有 PCS 关系

即使没有子节点，也产生一条空链 pcs(n, ⊣, ⊢)

论文规定，即使节点没有任何子节点，也要产生一条从列表开始直接指向列表结束的空链。

⊣→ ⊢

siblings 为空时的结果
Pcs.scalaline 117 · zip 构链
val chain =
  (ListStart +: siblings) zip
  (siblings :+ ListEnd)

// siblings 为空时：
//   ListStart +: Nil  ->  Seq(ListStart)
//   Nil :+ ListEnd    ->  Seq(ListEnd)
//   zip 得到          ->  (ListStart, ListEnd)
保证每个元素节点至少有一条 PCS 关系，后续算法无需为叶节点单独编写特殊分支。

relations 如何分解整棵树

入口 relations(root, labelOf)（line 113），递归函数 go 对每个节点执行四步

1
生成节点内容
val here = Content(
  labelOf(ref),
  ref.element.tag,
  ref.element.attributes,
  leafText(ref.element),
  leafIsCData(ref.element)
)
为当前节点生成一个 c(n, c)。
2
取得元素子节点
val kids =
  ref.element.childElements.zipWithIndex.map {
    case (c, i) => NodeRef(ref.path.child(i), c)
  }
只把 GenericElement 放进 PCS 链；GenericText 不作为独立结构节点。
3
生成 PCS 链
val siblings = kids.map(k => SiblingNode(labelOf(k)))
val chain    = (ListStart +: siblings) zip (siblings :+ ListEnd)
val pcsHere  = chain.map { case (p, s) => Pcs(labelOf(ref), p, s) }.toSet
若子节点为 [u1,u2]，chain 为 (⊣,u1) (u1,u2) (u2,⊢)。
4
递归并求并集
val below = kids.map(go)

RelationSet(
  pcsHere ++ below.flatMap(_.pcs),
  Set(here) ++ below.flatMap(_.content)
)
当前节点与所有后代的关系合并为一个 RelationSet。
论文把所有关系放在统一集合 Tk 中；Scala 实现为了类型安全，将它拆成 pcs 与 content 两个集合（RelationSet(pcs, content)）。
07

一个 IDML 示例

纯 reorder 如何体现在两个集合上

输入 XML
<Spread Self="us">
  <Rectangle Self="u1"/>
  <Rectangle Self="u2"/>
</Spread>
content 集合
Content("us", "Spread", …)
Content("u1", "Rectangle", …)
Content("u2", "Rectangle", …)
pcs 集合
Pcs("us", ListStart, u1)
Pcs("us", u1, u2)
Pcs("us", u2, ListEnd)
Pcs("u1", ListStart, ListEnd)
Pcs("u2", ListStart, ListEnd)

若把顺序改为 u2, u1，三个 Content 完全不变，而父节点的 PCS 关系全部改变：

content 集合三条不变
  • Content("us", "Spread", …)
  • Content("u1", "Rectangle", …)
  • Content("u2", "Rectangle", …)
pcs 集合（父节点 us）三条改变
  • Pcs("us", ListStart, u1)
  • Pcs("us", u1, u2)
  • Pcs("us", u2, ListEnd)
  • Pcs("us", ListStart, u2)
  • Pcs("us", u2, u1)
  • Pcs("us", u1, ListEnd)
结论：PCS 模型能够检测纯 reorder；而只比较属性的 EditDetector 检测不到这种变化。
08

节点标签如何映射到 IDML

论文假设 label 在所有版本中唯一且稳定

Pcs.scalaline 68 · label 规则
def label(ref: NodeRef): String =
  ref.self.getOrElse(ref.path.toString)
有 IDML Self
<Rectangle Self="u13d"/>
// label = "u13d"
没有 Self → 用路径
<Properties>…</Properties>
// label = "/0/2"
路径匹配的隐患：相同 path 字符串会在不同版本间被视为同一 label。只要结构不移动，这种位置匹配可以工作；一旦前面插入或删除 sibling，路径就会漂移，甚至匹配到错误节点。因此弱身份文档需要先经 ContentMatcher.matchedLabel 把 modified 节点映射回 base 标签。

代码与论文第 2.3 节的两个关键差异

实现更紧凑，但覆盖范围小于完整模型

差异一文本节点没有作为独立 PCS 节点

总结

对论文最核心思想的实现是准确的，代价是两个工程简化

准确实现的核心

  • 将有序 XML 树分解成 Content 集合与 PCS 邻接关系集合
  • 使内容更新、插入、删除、移动都能通过集合差异表达
  • 纯 reorder 可被 PCS 检测，属性级检测器无法覆盖

两个工程简化

  • 文本叶节点折叠进父元素的 Content
  • 不建立论文中的人工根节点 ⊥
  • 统一集合 Tk 拆为 pcs / content 两集合

这套表示对以 Self、属性和元素顺序为核心的 IDML 结构非常实用；但对 Story mixed content、根节点冲突和完整 XML Infoset 仍不够完整。
