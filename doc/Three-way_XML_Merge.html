Overview

Paper overview

Three-way merging is a common scenario: a document has a base version, two people each copy it and edit independently, and the changes must be merged back into a single document. For plain text, diff / patch solved this long ago; but they treat a file as an "ordered list of text lines" and handle tree-structured data such as XML poorly.

This paper presents a three-way merge for "document-oriented XML" (rich text, structured text, drawings, and other formats naturally modeled as ordered trees). Its core idea is not to record edit operations, but to detect edits by comparing the base tree with the modified trees, and then reconcile those edits into a merged tree.

§1 · Introduction

Background: from text merge to structural merge

Line-based merge tools treat a file as a one-dimensional sequence of lines. That model is adequate for source code and similar text, but trees can be manipulated in more complex ways: a node can be moved elsewhere, and an entire subtree can be reorganized. In a "line sequence" such changes appear as large deletions plus insertions, and the tool cannot recognize that "this is the same content, moved" — so it often fails when reorganization and detail edits are combined.

The author concedes that different XML formats have different semantics, so there is no single "correct" definition of a generic XML merge. But formats that are naturally ordered trees share enough traits for a generalized merge. And — just as diff3 does not understand source-code semantics yet often gives usable results — a successful merge often does not require understanding the full semantics of the data. To that end, the paper deliberately uses an easy-to-understand change-detection model, and reports conflicts in ambiguous situations rather than "cleverly" guessing.

§2 · Three-way merge framework

Two-phase framework: edit detection and reconciliation

The notation runs throughout: T0 the base tree, T1 and T2 the two modified trees, Tm the merge result, and T′ any one of the modified trees. Because the paper does not assume the actual edit scripts E1, E2 are known, the merge must proceed in two steps.

Difference from operation-log methods Many merge methods rely on a "record of edit operations". This paper does not — it recovers edits by comparing the trees themselves. That yields a useful property: any two trees can be merged even when their relationship is unknown, with no need to know which was edited from which, and no revision history.

§2.3 · Data model

The ordered-tree model and PCS relations

An XML document is modeled as an ordered tree with labeled nodes. Labels are unique across all documents and serve as node identity. Each node has "content" (node type, text data, or element name and attributes). To focus on the merge itself, the model omits comments, DTDs, entities, and so on — but these can be accommodated by adding node types.

Expressing a tree as a set of relations

The paper's key move: instead of drawing a tree as a graph, it expresses it as a set of two kinds of relations. This set representation is the common "currency" for everything that follows.

  • Content relation c(n, c): node n has content c.
  • Parent-child-successor relation (PCS) pcs(r, p, s): r is the parent of both p and s, and in r's child list s immediately follows p.

The two ends of a child list use special markers: ⊣ sits before the first child, and ⊢ sits after the last. They cannot be edited, so any changed node can always be assumed to have a predecessor and a successor.

§3 · Merge rules

Merge rules: node context at the center

The rules are not designed out of thin air; they are generalized from 37 hand-merged use cases (covering real scenarios such as concurrently editing a technical manual, maintaining web pages that share data, inline SVG updates, and a shared shopping list). The core concept from the analysis is "node context": a node's parent, predecessor, and successor. The merge's handling of structure is essentially "which node contexts to preserve in Tm".

  • Sameness. To reconcile changes from different trees, one must first decide "this is the same node". Otherwise a move in T1 cannot be matched to an update in T2.
  • Node context. The structure of the merge result is fixed by a set of node contexts required to appear in Tm.
  • Guard. Some contexts are additionally preserved to inhibit merging of changes that are too close together to safely assume are semantically independent.
  • Content-update propagation. A change to a node's content in T′ should also appear in Tm.
  • Insert propagation. A node inserted in T′ should appear in Tm, keeping the same context.
  • Delete propagation (with guard). A deleted node does not appear in Tm; but its context is preserved — if d is removed from the child list adb, then ab should appear as a sublist.
  • Move propagation. A move is understood as a relative position, not an absolute one; the destination and source contexts of a move are both expressed and preserved as node contexts; moves too close together are, as an exception, not merged.
  • Conflict identification. Certain combinations (e.g. both sides changing the same node's content) are treated as conflicts.
Why context is the key Expressing "where a node is" as "its parent, predecessor, and successor" lets insert, delete, and move all be unified as "assert or preserve certain PCS relations in Tm". A move can coexist with structural edits precisely because it fixes only relative adjacency, not the absolute position of an entire subtree.

§4 · Tree matching

Tree matching: establishing node identity

The first cornerstone of the merge is "sameness". Matching is expressed by the predicate m(n,m): true if and only if n and m are the same node. A matching can be read naturally as edits — an unmatched base node was deleted, an unmatched modified node was inserted, differing content is an update, and a differing position is a move.

A matching must satisfy a set of constraints (R1–R5): each node has at most one match in each other tree (R1, which rules out "multi-node glue" and "copy" — treated as delete + insert when encountered); and the matching is required to be an equivalence relation — reflexive (R3), symmetric (R4), transitive (R5) — partitioning all nodes into disjoint node classes. The paper assumes the matching is given as input; how to build matchings efficiently for documents without unique identifiers is an important practical issue, not developed here.

§5 · Change model

Change model: content and structural changes

The clever part: changes are expressed with exactly the same relations used to express a tree.

Consistency: a change set must not contradict itself

When multiple changes are placed in one set, it is required to be consistent — stating at most one content, one parent, one predecessor, and one successor for each node:

1. c(n,c) ∧ c(n,c′)        → c = c′      unique content
2. parent(r,n) ∧ parent(r′,n) → r = r′    unique parent
3. pcs(r,p,s) ∧ pcs(r,p′,s) → p = p′     unique predecessor
4. pcs(r,p,s) ∧ pcs(r,p,s′) → s = s′     unique successor

Conversely, a consistent relation set determines a tree unambiguously. The goal of the merge is to construct exactly such a consistent set.

§6 · Merge definition

The merge definition and algorithm

The merge combines the three trees' relation sets into one and then resolves contradictions. A few key objects:

  • Class representative. Each node class picks a representative (the node from the tree with the smallest index). T* denotes the set after replacing every node with its class representative.
  • Raw merge T*. The union of the three trees' relations. It is usually inconsistent — the same node carries conflicting content or positions from different trees. This is the "raw" merge.
  • Edit set E = T* − T*₀. Any relation that appears in a modified tree but not in the base tree is a detected edit.
  • Target Δ. A consistent set that contains all edits E and consists only of relations from the input trees (nothing is "made up").

Algorithm pseudocode

procedure merge(T0, T1, T2: Tree, m: Matching)
1 for 0 ≤ k < 3:
2     T := asChangeSet(Tk)
3     T*k := useClassRepresentative(T, m)
5 Δ := ∪ T*k                       initial = raw merge
6 for all δ ∈ Δ:
7     δ′ := nil
8     δ′ := getOtherContent(Δ, δ)
9     if δ′=nil then δ′ := getOtherRoot(Δ, δ)
10    if δ′=nil then δ′ := getOtherPredecessor(Δ, δ)
11    if δ′=nil then δ′ := getOtherSuccessor(Δ, δ)
12    if δ′≠nil:                     conflict found
13        if δ′ ∈ T*0:  Δ := Δ − {δ′}   drop base side
15        else if δ ∈ T*0: Δ := Δ − {δ}
17        else: conflict(δ, δ′)          both are edits → conflict
22 return Δ

Tm can be reconstructed by traversing from ⊥0 level by level along the PCS relations in Δ. There is also a trick: if some data must appear verbatim in Tm, simply do not match it to a base node, and its relations will be treated as edits and forcibly preserved.

§6.3 · Conflicts

Conflict types

A good merge should report conflicts "neither too many nor too few": it should not invent conflicts where there are none, nor "cleverly" auto-resolve ambiguous situations. Conflicts fall into two categories — C core, exposed when the algorithm fails to construct a consistent Δ; and O optional, which need separate detection in post-processing (and can be turned off for a more permissive merge).

C The same node's content is changed to different values in T1 and T2. The set contains both c(n, c1) and c(n, c2) with c1 ≠ c2, which cannot be consistent.

C Node m in T1 and node n in T2 are positioned such that Δ cannot be made consistent. The positional change can be a move, insert, or delete, so it subdivides into move/move, move/insert, move/delete, delete/delete, etc. The implementation can offer speculative resolutions for several of these (e.g. ignoring the repositioning from one side).

O The basic merge allows further modifications inside a deleted subtree, so by default it does not treat "one side deletes, the other edits" as a conflict — which can lose edits, hence it is optional detection. When enabled, it checks (Δ − Tm) ∩ E = ∅, i.e. the deleted part should contain no edits.

§6.4 · Properties

Properties of the merge

SymmetryThe result is independent of the order in which T1 and T2 are assigned — the merge only distinguishes "base vs modified", not which modified tree a node came from.
Edit preservationE ⊂ Δ, so all edits are preserved; if edits in deleted subtrees are treated as conflicts, then E ⊂ Tm.
Parallel edit modelDetected edits are inherently unordered and (within a single tree) independent of each other, avoiding any artificial ordering and the reconciliation complexity it would bring.
ExtensibilityThe formal model has been extended in later work to support "copy", and should generalize easily to an n-way merge.
§6.5 · Complexity

Computational complexity

Under the assumption that "the content size of an individual node has a constant bound", the algorithm runs in O(n log n) time, where n is the total number of nodes in the input trees. The analysis uses red-black trees (which give O(log n) lookup/insertion), and builds lookup tables for structural changes indexed by predecessor and successor — any lookup returns at most 3 relations (one per tree), so looking up a node's matches is constant-time.

§7 · Implementation & evaluation

Implementation and evaluation

The method is implemented as the open-source tool 3dm (which includes a heuristic tree matcher for building the matching). Of 37 study cases, 35 succeeded (omitting the parts that demonstrate "copy"); the other two do not fit this merge model; symmetry was also verified. The evaluation surfaced a few practical findings:

  • Document metadata (e.g. OpenOffice's <meta:date>) often changes inconsistently on both sides, a nuisance in real use.
  • A successful merge needs enough common structure around the changed area. For example, merging a paragraph <p>…555-1234…</p> with a change to a separate <phone>555-1234</phone> fails.
  • Structural edits that are too close also fail: bolding and italicizing the same <li> makes the text and italic block two separate nodes. Introducing a <div> to group logical entities fixes it.

These aside, overall performance is satisfactory, successfully merging the content of several concurrently edited OpenOffice, XML, and XHTML documents; the merge is also used for reconciling directory trees in a shared file system.

§8–§9 · Related work & conclusion

Related work and conclusion

The merge tools in Word, OpenOffice, and the like are based on pairwise comparison of documents, not three-way merging. The structured-merge methods in the literature (Asklund [12], Manger [8], DeltaXML [7], etc.) handle delete, update, and insert in largely the same way; the real difference is whether they support "move" and how they merge moves.

How this work positions itself Earlier methods' move rules are often tied to a specific domain (e.g. semantically aware source-code merging). This paper attempts to give more universally applicable move rules; this is also its main advantage over text-based merging and prior work — the ability to handle "large-scale reorganization" and "detail updates" at the same time.

Conclusion: the paper provides a set of examples, use cases, and rules for designing and testing three-way merges of document-oriented XML; the method is based on empirical rules, easy to implement, computationally efficient, and intuitive in its handling of node operations. Future directions: extend to unordered trees, and study how to specialize the merge with domain-specific knowledge, so as to efficiently reuse the functionality of a generalized merge.
